# Transactional Email Provider — Design Spec

**Date:** 2026-05-19
**Status:** Approved (brainstorming)
**Topic:** Security backlog **P1** — wire a transactional email provider (Resend) and Better Auth's email callbacks. Hard dependency for P2 (email verification) and P3 (password reset / recovery).

---

## 1. Goal & scope

Give TuringCare the ability to send transactional email, and connect Better
Auth's email callbacks so the verification + password-reset *senders* are
functional — **without** changing any user-facing behavior yet.

**In scope:** a reusable, provider-isolated `sendEmail` capability (Resend);
two email templates; Better Auth `sendResetPassword` +
`emailVerification.sendVerificationEmail` callbacks wired; env/secrets/DNS;
tests.

**Explicitly out of scope (separate specs):** P2 — enabling
`requireEmailVerification` + any verify-email UX; P3 — the password-reset
request/confirm **frontend**. No new web routes or UI in this phase.

**No user-visible change:** `requireEmailVerification` stays OFF, so accounts
remain immediately usable exactly as today. A verification email is sent on
sign-up but nothing enforces it; the existing `/forget-password` endpoint
(already present and rate-limited 3/60s) starts actually delivering mail.

### Decisions locked during brainstorming

| Decision | Choice |
|---|---|
| Provider | **Resend** (official `resend` npm SDK) |
| Phase scope | Sending capability **+** Better Auth hooks wired; `requireEmailVerification` OFF; no frontend |
| Dev/CI when `RESEND_API_KEY` unset | **Log-only no-op** (no network, resolves success); prod requires the key |
| Sending domain | Verified subdomain `send.turingcare.dog` (SPF/DKIM/DMARC in Cloudflare) |
| From address | `TuringCare <noreply@send.turingcare.dog>` (prod); dev default placeholder |
| Templates | Plain inline-styled HTML, no React Email dependency (YAGNI) |

## 2. Architecture & module boundary

Provider-isolated email unit; callers depend only on `sendEmail` + the two
template builders. The Resend SDK is imported in exactly one file.

### `apps/api/src/email/send-email.ts`
```
export class EmailSendError extends Error {}
export interface SendEmailArgs { to: string; subject: string; html: string; text: string; }
export async function sendEmail(args: SendEmailArgs, deps?: { client?: ResendLike; from?: string; apiKey?: string }): Promise<void>
```
- Minimal validation: non-empty `to` and `subject` → otherwise `EmailSendError`.
- Resolve `apiKey` (default `env.RESEND_API_KEY`), `from` (default
  `env.EMAIL_FROM`), `client` (default: a lazily-constructed Resend client when
  an API key exists; injectable for tests).
- **No API key** → `console.info("[email:dev]", { to, subject })` (subject/to
  only — never the link/token body) and resolve. No network, never throws.
- **API key present** → send via the client; a provider/SDK error → throw
  `EmailSendError` (message carries provider status/context only — no API key,
  no PII, no token).
- `ResendLike` = the minimal interface used (`emails.send({ from, to, subject, html, text })`), so the dependency is a narrow seam, not the whole SDK type.

### `apps/api/src/email/templates.ts`
```
export function verificationEmail(url: string): { subject: string; html: string; text: string }
export function passwordResetEmail(url: string): { subject: string; html: string; text: string }
```
- Pure functions. Plain inline-styled HTML + a `text` fallback. Each embeds
  `url` exactly once in both `html` and `text`. TuringCare voice, no tracking
  pixels, no external assets.

### `apps/api/src/env.ts` (additive)
- `RESEND_API_KEY: z.string().optional()` — absence = dev log mode.
- `EMAIL_FROM: z.string().default("TuringCare <noreply@send.turingcare.dog>")`.

`resend` added to `apps/api` dependencies (only `send-email.ts` imports it).

## 3. Better Auth integration

In `apps/api/src/auth.ts`, add to the `betterAuth({…})` config:

- `emailAndPassword.sendResetPassword: async ({ user, url }) => { … }` — wraps
  `sendEmail({ to: user.email, ...passwordResetEmail(url) })`.
- `emailVerification: { sendOnSignUp: true, sendVerificationEmail: async ({ user, url }) => { … } }`
  — wraps `sendEmail({ to: user.email, ...verificationEmail(url) })`.
- **`requireEmailVerification` is NOT set** (stays OFF).

`url` is generated by Better Auth (token + `BETTER_AUTH_URL`); this phase only
sends it. Both callbacks isolate failures (see §4). No change to existing
`databaseHooks`, rate limiting, adapter, or `advanced`.

---

## 4. Error handling & reliability

- `sendEmail` dev/log path: never throws, never networks.
- `sendEmail` provider path: input-validates; provider failure → `EmailSendError`
  with non-sensitive context.
- **Auth callbacks swallow errors:** both wrap `sendEmail` in try/catch, log
  `{ event, userId }` (never the link/token/email body), and resolve — a flaky
  provider must never break sign-up or `/forget-password`. Same fire-and-forget
  principle as `recordEvent`. Accepted trade-off: a transient provider outage
  can drop a verification email (harmless while enforcement is OFF) or a reset
  email (user can re-request).
- Secrets: `RESEND_API_KEY` only read from `env` (Fly secret in prod); never
  logged, never committed, never in test fixtures.

## 5. Configuration, secrets & DNS (operator checklist)

Code-side: `env.ts`, `.env.example` (key blank locally → dev log mode;
documents `EMAIL_FROM`), and `DEPLOY.md` secrets table updated with
`RESEND_API_KEY` + `EMAIL_FROM`.

Operator actions (documented in the spec/DEPLOY.md, **not** code):
1. Create the Resend account/API key.
2. Add domain `send.turingcare.dog` in Resend; add the generated SPF, DKIM,
   and a DMARC record in Cloudflare DNS; wait for Resend to verify.
3. `fly secrets set --app turingcare-api RESEND_API_KEY=… EMAIL_FROM='TuringCare <noreply@send.turingcare.dog>'`.

Until the domain is verified + secret set, prod simply runs in log mode for
email (no crash) — deploy is not blocked by DNS propagation.

## 6. Testing

Repo Vitest; `.env` auto-loaded; **no network in any test**; CI never sends.

- **`templates.test.ts`** — both builders return non-empty `subject`/`html`/
  `text`; `html` and `text` each contain the passed `url` exactly once; no
  unsubstituted `${}`/placeholder markers.
- **`send-email.test.ts`** — (a) no API key → no client call, logs once,
  resolves; (b) injected mock client + key → called once with
  `{ from, to, subject, html, text }`; (c) mock client rejects → `EmailSendError`;
  (d) empty `to`/`subject` → `EmailSendError`, client not called. Resend SDK
  never instantiated against the network (dependency-injected).
- **`auth-email.test.ts`** (integration, real Better Auth + DB) — signing up
  triggers the verification callback with the new user's email (assert via an
  injected/stubbed `sendEmail` spy); a `sendEmail` that throws does **not**
  fail sign-up (response still 2xx, user row created).
- Full gate green: `pnpm biome check .`, `pnpm -r exec tsc --noEmit`,
  `pnpm -r test`, `pnpm -r build`.
